3. نموذج الأمان والصلاحيات

كل الجداول الحساسة مفعّل عليها Row Level Security. دور المستخدم لا يُستمد من بيانات يرسلها التطبيق، بل من JWT claim باسم app_metadata.role.

الدورمصدر الدورالوصول
زائرلا يوجد sessionقراءة الكتالوج والعروض المنشورة فقط.
customerأي مستخدم Auth بدون claim adminبياناته الشخصية وحجوزاته وإشعاراته ومفضلته.
adminauth.jwt() -> 'app_metadata' ->> 'role' = 'admin'إدارة الحجوزات والكتالوج والعروض وقراءة audit log.
مهم: لا تستخدم user_metadata.role لتحديد صلاحيات المدير. يجب أن يكون الدور في raw_app_meta_data حتى لا يستطيع المستخدم تغييره بنفسه.

إنشاء مستخدم مدير

-- نفّذ من جلسة SQL إدارية فقط، وليس من التطبيق
update auth.users
set raw_app_meta_data = coalesce(raw_app_meta_data, '{}'::jsonb)
  || '{"role":"admin"}'::jsonb
where email = 'admin@example.com';

بعد تغيير الدور يحتاج المستخدم إلى تسجيل الدخول مجددًا أو تجديد JWT.

4. المصادقة Auth

المسار القياسي للمطور هو استخدام Supabase SDK native. يمكن أيضًا استخدام HTTP مباشرة كما في الأمثلة.

4.1 إنشاء حساب

POST /auth/v1/signup

{
  "email": "customer@example.com",
  "password": "StrongPassword123!",
  "data": {
    "full_name": "Customer Name",
    "phone_number": "+971501234567"
  }
}
  • التطبيق الحالي يطبع رقم الإمارات إلى صيغة +9715XXXXXXXX.
  • البريد يستخدم للدخول واسترجاع كلمة المرور.
  • الهاتف يخزن داخل metadata وcustomer_profiles للتواصل، وليس تسجيل دخول بالهاتف.
  • إذا كان Email Confirmation مفعّلًا فلن يرجع session حتى تأكيد البريد.

4.2 تسجيل الدخول

POST /auth/v1/token?grant_type=password

{
  "email": "customer@example.com",
  "password": "StrongPassword123!"
}

الاستجابة تحتوي عادةً على access_token وrefresh_token وبيانات المستخدم. خزّن session باستخدام secure storage في الجوال، وليس plain local storage.

4.3 تحديث الحساب

PUT /auth/v1/user

{
  "password": "NewStrongPassword123!",
  "data": { "full_name": "New Name" }
}

4.4 استرجاع كلمة المرور

POST /auth/v1/recover

{
  "email": "customer@example.com"
}
رابط الاسترجاع الحالي في الويب مبني على window.location.origin. لتطبيق Native يجب إضافة Redirect URL مثل purity://auth/reset في Supabase Auth ثم تمريره من تطبيق الجوال.

4.5 تسجيل الخروج

POST /auth/v1/logout مع Access Token.

10. Realtime

التطبيق الحالي يشترك في تغييرات جدول public.bookings:

  • العميل: filter = user_id=eq.<USER_ID>.
  • المدير: كل تغييرات الجدول.
  • بعد أي تغيير يعاد تحميل الحجوزات والإشعارات.
const channel = supabase
  .channel(`customer_updates_${userId}`)
  .on('postgres_changes', {
    event: '*',
    schema: 'public',
    table: 'bookings',
    filter: `user_id=eq.${userId}`
  }, (payload) => {
    // refetch bookings and notifications
  })
  .subscribe();

لا يوجد Push Notification في هذا العقد. Realtime يعمل عندما يكون التطبيق مفتوحًا أو الاتصال بالخدمة قائمًا.

11. الأخطاء والاستجابة

REST API تعيد أخطاء Supabase القياسية، وغالبًا بالشكل التالي:

{
  "code": "42501",
  "details": null,
  "hint": null,
  "message": "new row violates row-level security policy"
}
الحالة/الكودالسبب المحتملتصرف تطبيق الجوال
401 / 403جلسة منتهية أو RLS يمنع العملية.اعمل refresh للـ session، ثم اطلب تسجيل الدخول عند الحاجة.
409تعارض unique مثل wishlist أو رقم الهاتف.اعرض رسالة مفهومة ولا تعيد الإنشاء بلا فحص.
400حقل ناقص أو نوع غير صحيح.تحقق محليًا قبل الإرسال.
42501RLS policy رفضت الطلب.لا تحاول تجاوزها بإرسال user_id مختلف.
429حدود Auth أو ضغط/إساءة استخدام.backoff وإعادة المحاولة بحذر.
5xx / networkتعطل Supabase أو الشبكة.لا تنشئ حجزًا محليًا على أنه محفوظ؛ استخدم idempotency بعد إضافة backend مناسب.
منع التكرار: عقد الحجز الجديد يستخدم p_client_request_id. أعد استخدام نفس القيمة عند إعادة المحاولة بعد timeout.

12. تعليمات تطبيق الجوال

12.1 دورة التشغيل الموصى بها

  1. أنشئ Supabase client من URL وanon/publishable key.
  2. استدعِ getSession() عند بدء التطبيق.
  3. استمع إلى تغييرات Auth لتحديث حالة المستخدم.
  4. بعد الدخول، استخدم Access Token تلقائيًا مع REST أو SDK.
  5. لا تثق بالسعر المحسوب في التطبيق؛ اعرضه للمستخدم فقط.
  6. عند انتهاء session، استخدم refresh token أو اطلب login.
  7. عند logout امسح session من Secure Storage.

12.2 مثال TypeScript باستخدام Supabase SDK

import { createClient } from '@supabase/supabase-js';

const supabase = createClient(SUPABASE_URL, SUPABASE_ANON_KEY);

const { data: auth, error: loginError } =
  await supabase.auth.signInWithPassword({
    email,
    password,
  });

if (loginError) throw loginError;

const { data: bookings, error } = await supabase
  .from('bookings')
  .select('*')
  .order('created_at', { ascending: false });

if (error) throw error;

12.4 صلاحيات الهاتف

  • الموقع الجغرافي اختياري؛ يستخدم فقط للحصول على latitude/longitude للحجز.
  • تطبيق الجوال يجب أن يطلب permission للموقع قبل الحجز، مع السماح بإدخال العنوان يدويًا.
  • لا ترسل مفاتيح خرائط أو أسرار server من التطبيق إلا إذا كانت public ومقيدة بالنطاق.

14. قائمة تسليم لمطور تطبيق الجوال

قبل بدء التطوير: أعطِ المطور Supabase URL وanon key فقط، وطبّق ملفات SQL بالترتيب: bookings ثم wishlist ثم catalog ثم api، وتأكد من أن host يعمل من شبكة الهاتف.
  • تفعيل Email provider في Supabase Auth.
  • تحديد سياسة Email Confirmation المطلوبة.
  • تسجيل redirect URLs الخاصة بـ iOS وAndroid.
  • اختبار customer login وrefresh وlogout.
  • اختبار RLS بحسابين مختلفين: كل عميل يرى بياناته فقط.
  • اختبار إنشاء حجز وظهور notification تلقائيًا.
  • اختبار admin status update وaudit log.
  • اختبار انقطاع الشبكة وعدم تكرار الحجز.
  • عدم وضع service role key أو CRON_SECRET داخل التطبيق.
  • الاتفاق على versioning قبل تغيير أسماء الحقول أو أنواعها.

ترتيب العمل الموصى به قبل الإنتاج

  1. إصلاح اتصال Supabase والتحقق من schema في المشروع الصحيح.
  2. تأمين create booking عبر RPC/Edge Function وحساب السعر على الخادم.
  3. إضافة idempotency وvalidation للخدمات والمناطق والتواريخ.
  4. إضافة deep links وPush notifications.
  5. إضافة contract tests وتثبيت إصدار API.

15. سياسة الاحتفاظ بالبيانات والحذف المنطقي

Supabase هو المصدر الوحيد لبيانات التطبيق. لا يستخدم التطبيق تخزين المتصفح للحجوزات أو المفضلة أو الكتالوج، ولا ينفذ حذفًا فعليًا لسجلات التطبيق.

  • تستخدم الجداول عمود deleted_at لإخفاء السجل مع الاحتفاظ به.
  • أرشفة الحجز تتم بتحديث السجل إلى deleted_at مع الاحتفاظ ببيانات العميل وسجل التدقيق.
  • إزالة المفضلة تتم عبر set_wishlist_item ولا تستخدم DELETE.
  • تمنع قاعدة البيانات أي DELETE مباشر على جداول التطبيق من خلال Trigger وصلاحيات SQL.
  • يجب تطبيق supabase_soft_delete.sql بعد مخططات bookings وwishlist وcatalog وapi.
